## Why
The production build has no hosted server, so "Phòng online" cannot work. The user decided: **hide the online button and offer LAN rooms instead** —
two phones on the same Wi-Fi (or one phone's hotspot) play each other with **no server and no Internet**. One phone hosts the authoritative room inside the app.

## Feature specification

### F1 — Home
- Replace the "Phòng online" button with **"Chơi LAN"** (en: "LAN play"), same blue style, opens the LAN screen.
- The online entry is hidden, not deleted: gate it behind `process.env.EXPO_PUBLIC_ONLINE_ENABLED === '1'` (default off). When on, Home shows both buttons. Internet code paths and their tests stay intact.
- The How-to-play sheet gains one short line: LAN needs both phones on the same Wi-Fi or hotspot.

### F2 — LAN screen (reuse/extend `RoomsScreen` visual language: paper panel, folk buttons)
- **Tạo phòng LAN** — become the host (F3).
- **Tìm phòng** — list of rooms discovered on the network (F5): each row shows host label and room code; tap to join. Empty state: "Chưa thấy phòng nào" + a hint to check both phones are on the same Wi-Fi/hotspot; a visible "Quét lại" action; scanning indicator.
- **Nhập địa chỉ** — manual fallback: host address field (`192.168.1.23` or `192.168.1.23:PORT`) + 5-character room code + **Vào phòng**. Reuse the existing code input, paste button and validation style.
- Errors, in both languages: not on Wi-Fi/hotspot (no local IPv4), host not reachable / timed out, room full, room closed, wrong code, incompatible version.
- Back returns Home and stops any scan.

### F3 — Hosting
- Starts an in-app authoritative room (the same `OnlineRoomController` logic) and a TCP listener on a free port.
- Lobby shows: room code (large), **host address `IP:port`** (copyable), a short "Người chơi cùng Wi-Fi sẽ thấy phòng này" line, opponent slot, **Share** (text contains code + address), Leave.
- The host is also player A, using the same transport abstraction with an in-process link (no socket to itself).
- While hosting/playing as host: keep the screen awake (`expo-keep-awake`); if the host app goes to background, the existing 25 s reservation/forfeit rules apply to the host seat like any player — do not invent new rules. Show a one-line warning on the host lobby: "Giữ ứng dụng mở trong khi chơi".
- Stopping the host (leave, match abandoned, app closed) closes the listener, stops advertising and disposes the controller (no leaked timers/sockets).
- Exactly one hosted room per app instance; third connection gets `ROOM_FULL`.

### F4 — Joining and playing
- Join via discovery row or manual address. After join the flow is identical to today's online flow: Lobby → Draft → Board → Result → rematch / leave, including reveal moment, round banner, exit dialog, forfeit, `opponentLeft`.
- Reconnect: if the socket drops, the existing Reconnecting screen retries the same host address for the 25 s reservation; success resumes at the server phase; expiry returns to the LAN screen with an error. Host loss (host app killed) ends in "host unreachable" for the joiner.
- Privacy guarantees are unchanged: a client only ever receives its own projection.

### F5 — Discovery
- Host advertises a service (suggested `_baobuakeo._tcp`, name includes room code) via mDNS/DNS-SD; joiners browse it. TXT/metadata: protocol version, room code, whether a seat is free.
- Full rooms disappear from (or are disabled in) the list. Stale entries are removed when the service is lost or after a timeout.
- Discovery is best-effort. The manual address path (F2) must work even if discovery is unavailable or the library cannot be used.

### F6 — Wire protocol (LAN)
- Newline-delimited JSON over TCP, request/response with a request id, mirroring `OnlineRoomClient` operations: `hello` (protocol version check), `join`, `reconnect`, `snapshot`, `action`, `leave`. Server may also push snapshots; the client may keep polling at the existing cadence if that is simpler — do not regress the screens' ordering logic (`acceptBoardSnapshot`, revision/serverNow).
- Limits: max frame size (16 KB), reject malformed frames, per-connection rate limit (reuse `MessageRateLimiter`), idle timeout, max 4 simultaneous sockets (2 players + reconnect headroom).
- Auth: same as HTTP — session id + reconnect token returned by `join`; `action`/`snapshot`/`leave` require the token. Room code is required to join.
- Version mismatch → explicit error surfaced as "incompatible version".

### F7 — Architecture constraints
- Move the room controller (and `MessageRateLimiter`) into a shared, platform-neutral place importable by both `server` and `mobile` (new workspace package or `game-core` subpath — your call; state why). Inject randomness/ids (`randomInt`, `randomUUID`) instead of importing `node:crypto`; server passes `node:crypto`, mobile passes `expo-crypto`-based implementations (must be cryptographically secure on device). All 26 server tests must still pass unchanged in intent.
- Introduce one transport seam on mobile so screens do not care whether the room is Internet or LAN (e.g. a factory/provider selecting `OnlineRoomClient` by the active session). Screens must not grow per-transport branches beyond choosing copy.
- Native deps: pick maintained libraries that work with RN 0.88 new architecture + Expo SDK 58 CNG (TCP sockets, mDNS/zeroconf, `expo-network` for the local IPv4, `expo-keep-awake`). Add config/permissions through `app.json`/config plugins, never by hand-editing `mobile/android` (Android: e.g. `CHANGE_WIFI_MULTICAST_STATE`; iOS keys `NSLocalNetworkUsageDescription`/`NSBonjourServices` may be added to config but iOS is not built or tested).
- Unit tests must not load native modules: keep them behind boundaries with injectable fakes (as `interstitial-gate.ts` does).
- All new user-facing strings in `mobile/src/i18n/vi.ts` and `en.ts`. Terminology: Ván = match, Lượt = round.
